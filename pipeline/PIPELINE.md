# Конвейер разработки на основе ИИ-агентов

Версия: 1.1  
Назначение: воспроизводимый процесс разработки, в котором большая модель координирует проект, модель-аналитик готовит требования и план, субагенты-разработчики пишут код, а независимые субагенты-контролёры тестируют и проводят ревью.

## 0. Проекты и режимы задач

Конвейер мультипроектный. Каждая папка проекта имеет собственные артефакты:

```text
<PROJECT>/
├── pipeline/
│   ├── config.json
│   ├── tasks/
│   ├── templates/
│   └── scripts/
├── .opencode/
│   ├── agents/
│   └── commands/
└── AGENTS.md
```

Подключение нового проекта:

```bash
python pipeline/scripts/init_project.py --path "<путь к проекту>" --name "<имя>" --stack "<стек>"
```

Без `--path` проект создаётся в `projects/<имя>`. Скрипт не перезаписывает существующие файлы без `--force`. Реестр проектов хранится в `pipeline/projects.json` рабочего каталога конвейера; благодаря нему команды находят задачу по ID без указания пути.

Все скрипты принимают `--project "<путь>"`. Если путь не указан, используется локальный проект, затем реестр.

Задачи бывают двух режимов:

| Режим | Когда используется | Что делает аналитик | Что делает разработчик |
|---|---|---|---|
| `greenfield` | разработка с нуля | предлагает стек, структуру, каркас | создаёт каркас, зависимости, точку входа, тесты, README |
| `improvement` | доработка существующего | изучает затронутые модули и регрессию | меняет только затронутые файлы, сохраняет совместимость |

Режим фиксируется в `00-task.md`, `status.json` и разделе «0. Контекст проекта» в `01-spec.md`. Шлюз `analysis` не пропустит задачу, если режим или стек не конкретизированы.

## 1. Состав конвейера

| Роль | Агент | Задача | Результат |
|---|---|---|---|
| Координатор | `orchestrator` | Управляет задачей, запускает субагентов, собирает результат | План, задания, статус, итоговый отчёт |
| Аналитик | `analyst` | Превращает ТЗ в спецификацию и план | `01-spec.md`, `02-plan.md` |
| Разработчик | `developer` | Выполняет одно задание DEV-XX | Код, тесты, `04-development/DEV-XX-report.md` |
| Тестировщик | `tester` | Независимо проверяет результат | `05-verification/test-report.md` |
| Ревьюер | `reviewer` | Проверяет качество кода | `05-verification/review-report.md` |
| Безопасность | `security` | Проверяет уязвимости и секреты | `05-verification/security-report.md` |

Человек утверждает план и принимает результат. Без этого конвейер не проходит дальше соответствующего шлюза.

## 2. Схема процесса

```text
Задача / ТЗ
   │
   ▼
[0] Приём и регистрация (orchestrator)
   │
   ▼
[1] Анализ и спецификация (analyst)
   │
   ▼
[2] План и согласование человеком  ◄── G1: план утверждён
   │
   ▼
[3] Декомпозиция и запуск субагентов (orchestrator)
   │
   ├── developer DEV-01 ──┐
   ├── developer DEV-02 ──┤ параллельно
   └── developer DEV-N ───┘
   │
   ▼
[4] Тестирование и ревью (tester + reviewer + security)
   │
   ├── PASS/APPROVE ──► [5] Интеграция и приёмка
   │
   └── FAIL/REQUEST CHANGES ──► [6] Доработка
                                   │
                                   └──► повторная проверка (не более 3 итераций)
```

## 3. Этапы и шлюзы

| Этап | Кто выполняет | Вход | Результат | Шлюз |
|---|---|---|---|---|
| 0. Приём | `orchestrator` | Задача, ТЗ, обращение | `00-task.md`, `status.json` | G0: задача зарегистрирована |
| 1. Анализ | `analyst` | `00-task.md`, кодовая база | `01-spec.md`, `02-plan.md` | G1: спецификация полная, критерии проверяемы |
| 2. Согласование | человек + `orchestrator` | План | `Decision: approved` в `02-plan.md` | G2: план утверждён человеком |
| 3. Декомпозиция | `orchestrator` | Утверждённый план | `03-assignments/DEV-XX.md` | G3: задания атомарные и готовы |
| 4. Разработка | `developer` | Задание, спецификация, план | Код, тесты, отчёт DEV-XX | Самопроверка пройдена |
| 5. Проверка | `tester`, `reviewer`, `security` | Код, критерии, `checks.log` | Отчёты с verdict | G4: PASS/APPROVE, критических дефектов нет |
| 6. Доработка | `developer` + контролёры | Дефекты | Исправления, повторная проверка | Не более 3 итераций |
| 7. Интеграция | `orchestrator` | Принятые изменения | Собранная версия, регрессия | G5: регрессия пройдена |
| 8. Приёмка | человек + `orchestrator` | Пакет изменений | `06-acceptance.md` | G6: результат принят |
| 9. Передача | `orchestrator` | Все артефакты | Метрики, запись в базу знаний | Задача закрыта |

## 4. Правила согласования плана

План утверждается только человеком. Координатор не имеет права самостоятельно перевести задачу в разработку.

Порядок:

1. Аналитик заполняет `02-plan.md`, в блоке Approval оставляет `Decision: pending`.
2. Координатор показывает план человеку: состав работ, сроки, риски, критерии приёмки.
3. Человек утверждает план командой:

```bash
python pipeline/scripts/approve_plan.py --task TASK-0001 --by "Фамилия И.О." --comment "Согласовано"
```

4. Координатор проверяет шлюз:

```bash
python pipeline/scripts/check_gate.py --task TASK-0001 --gate plan
```

5. Только после успешной проверки запускаются разработчики.

Если план отклонён:

```bash
python pipeline/scripts/approve_plan.py --task TASK-0001 --by "Фамилия И.О." --reject --comment "Причина"
```

Задача возвращается аналитику.

## 5. Цикл доработки

1. Тестировщик и ревьюер фиксируют дефекты с ID, серьёзностью, сценарием, ожидаемым и фактическим результатом.
2. Координатор собирает дефекты в список и создаёт задания на доработку.
3. Разработчик исправляет только указанные дефекты, не расширяя scope.
4. Проверка повторяется полностью: тесты, ревью, при необходимости безопасность.
5. Счётчик итераций увеличивается в `status.json`.
6. После 3 итераций задача эскалируется человеку. Автоматический цикл останавливается.

Правила:

- Нельзя вернуть задачу с формулировкой «сделать лучше» — только с конкретным воспроизводимым замечанием.
- Нельзя принимать результат с открытыми блокирующими или критическими дефектами.
- Если проблема в требованиях, задача возвращается аналитику, а не «лечится» кодом.
- Человек может остановить конвейер на любом этапе.

## 7. Команды OpenCode

| Команда | Назначение |
|---|---|
| `/pipeline-init <путь>` | Подключить папку проекта к конвейеру |
| `/pipeline-start <описание>` | Создать задачу, запустить анализ |
| `/pipeline-plan <ID>` | Проверить анализ и показать план на утверждение |
| `/pipeline-build <ID>` | Проверить утверждение плана и запустить разработку |
| `/pipeline-verify <ID>` | Запустить тесты, ревью и безопасность |
| `/pipeline-rework <ID>` | Запустить цикл доработки по дефектам |
| `/pipeline-status <ID>` | Показать статус и артефакты |
| `/pipeline-accept <ID>` | Провести приёмку после подтверждения человеком |

## 8. Скрипты

| Скрипт | Назначение |
|---|---|
| `python pipeline/scripts/init_project.py --path "<проект>"` | Подключить проект: скопировать каркас, создать реестр |
| `python pipeline/scripts/new_task.py --project "<проект>" --title "..." --mode improvement` | Создать задачу из шаблонов |
| `python pipeline/scripts/approve_plan.py --task TASK-0001 --project "<проект>" --by "..."` | Утвердить или отклонить план |
| `python pipeline/scripts/check_gate.py --task TASK-0001 --project "<проект>" --gate plan` | Проверить шлюз |
| `python pipeline/scripts/run_checks.py --task TASK-0001 --project "<проект>"` | Запустить build/lint/typecheck/test |
| `python pipeline/scripts/status.py` | Показать все задачи по всем проектам |
| `python pipeline/scripts/status.py --task TASK-0001` | Показать детали задачи; проект ищется по реестру |

Шлюзы: `intake`, `analysis`, `plan`, `development`, `verification`, `acceptance`.

## 9. Настройка

Основные параметры находятся в `pipeline/config.json`:

```json
{
  "max_iterations": 3,
  "branch_prefix": "pipeline/",
  "build_command": "",
  "lint_command": "",
  "typecheck_command": "",
  "test_command": ""
}
```

Заполните команды под свой стек. Если команда пустая, `run_checks.py` пропускает её и пишет предупреждение в `checks.log`.

Примеры:

```json
{
  "build_command": "npm run build",
  "lint_command": "npm run lint",
  "typecheck_command": "npm run typecheck",
  "test_command": "npm test"
}
```

```json
{
  "build_command": "python -m compileall -q .",
  "lint_command": "python -m ruff check .",
  "typecheck_command": "python -m mypy .",
  "test_command": "python -m pytest -q"
}
```

## 10. Безопасность

- Субагенты работают в изолированной среде и не имеют доступа к продуктиву.
- Разработчикам запрещены `git push`, merge в защищённые ветки, деплой и удаление данных.
- Секреты не передаются в промпты и не коммитятся.
- Тестировщик и ревьюер не являются авторами проверяемого кода.
- Для задач с риск-меткой `high`, `security` или `data` обязательна проверка `security`.
- Все изменения проходят через систему контроля версий и логируются.

## 11. Метрики

- Lead Time — от регистрации до приёмки.
- Cycle Time — время выполнения без ожиданий.
- First Pass Yield — доля задач, принятых с первой итерации.
- Число итераций доработки.
- Defect Escape Rate — дефекты после приёмки.
- Стоимость задачи: токены, инфраструктура, человеко-часы.
- Доля задач с полным набором артефактов.

## 12. Ограничения

- Качество результата зависит от качества входного ТЗ.
- Сложные архитектурные решения требуют участия человека.
- Автономность субагентов ограничена правами и sandbox.
- Для критичных систем обязательна усиленная человеческая приёмка.
- Конвейер не заменяет ответственность руководителя и заказчика.
